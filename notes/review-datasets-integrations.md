## Findings that matter before the demo

1. **Payload grounding is absent, even when the live planner succeeds.** `src/core/fixtures.ts:27` derives email arguments from fixed `CUSTOMER.contact`, not the thread or step. `src/tools/registry.ts:32` ignores the job and returns the same draft. The source scenario says `dana.okafor@northwind.example`, outage `14:05–17:10 UTC`, replay complete `18:30`; actual proposal uses `dana@northwind.example`, `09:12–12:04 UTC`, replay `12:40`. This is deterministic fixture drift, not a model hallucination. Store a canonical scenario/customer/incident context, produce drafts from that context, and compare the recipient and factual claims with their sources before proposing a commit.

2. **Fallback changes the user's job.** `src/agent/plan.ts:123` uses the same fixture when the key is missing, stub mode is set, either model request fails, or planning throws. `src/channel/listener.tsx:279` additionally substitutes the fixture for mentions of 80 characters or fewer. A short real request therefore becomes Northwind work even with a working model. A fixture should be an explicit demo selection. Otherwise preserve the original request and show `planning_failed` or `needs_context`. Persist `planOrigin`, source hash and fallback reason so a polished card cannot hide substituted input.

3. **Step identity is a state-machine boundary.** `src/agent/plan.ts:120` converts returned JSON without checking uniqueness. Core `updateStep` patches every matching ID. Duplicate IDs are valid under the submitted schema, and the reproduced collision made an email step look completed by a search. Reject duplicate/empty IDs, delimiter collisions, unsupported kinds and tools before persistence; bound step count and ID length. Generate stable internal step IDs separately from model-provided display labels if plans will be revised.

4. **Schema enforcement is remote; constraints are display text.** `src/agent/openrouter.ts:45` casts parsed JSON to a TypeScript type. It performs no runtime validation. OpenRouter's documented `require_parameters: true` setting is correctly included, but does not provide domain checks or uniqueness. The executor never evaluates constraints against payloads. A `Do not promise a credit` chip is visible context for a reviewer, not an enforced financial policy. Introduce local shape validation and explicit executable policies for supported restrictions, retaining source/author provenance for every policy. [OpenRouter structured outputs](https://openrouter.ai/docs/guides/features/structured-outputs).

5. **Tool success can mean that no work was implemented.** `src/tools/registry.ts:58` returns a success string for unsupported reversible tools, which core marks `done`. `tasks.create` only returns text saying two tasks were created; it creates no task records. The planner's tool enum uses `write_to_work_order`, while the default core fixture uses `tasks.create`. Use an explicit unavailable/blocked outcome and display the actual artifact count. A task plugin will need persistent task IDs and dedupe, not a string that claims task creation.

6. **Planning needs business-level observability.** There are two simultaneous model calls per plan, no application-level timeout/token cap, and all response metadata is discarded. A failure in either call discards both useful outputs into fixture fallback. Record input snapshot hash, plan/constraint provenance, request ID, model/provider, usage, timings, validation outcome and fallback reason. Display these alongside durable step state and ledger receipts. A routed LLM call proves that computation happened; it does not prove a job progressed or a message was sent.

The live injection check is encouraging and narrow: this particular input did not persuade this model to propose a send. The structural proof remains stronger: known commit tools are forced through the allowlist and an unauthorized actor cannot approve them. Stub-only injection tests do not test the model's handling of injected content.

## Ambiguous is reachable; the new document mirror is not wired into the lifecycle

The new `src/mirror/ambiguous.ts` is a real plain-fetch MCP client, and `src/mirror/index.ts` can write a local Markdown file and create/update an Ambiguous document. Nothing outside the mirror's own assertion script calls `mirror` or `mirrorSoon` yet. The checked-in execution registry still maps every commit tool to the local outbox. Thus a document integration exists, but normal worker/approval transitions do not invoke it, and mail remains stubbed. Having configuration keys or an installed reviewer plugin does not wire that lifecycle.

The read-only probe used only the configured host and key from the main checkout; it did not copy `.env`, invoke `tools/call`, inspect workspace documents, or create an identity. `initialize` took 764 ms, `tools/list` took 836 ms, both with protocol `2025-03-26`. Server metadata was `ambiguous-workspace` version `0.1.0`. The listing was complete at 856 advertised tools. That establishes connectivity and advertised capabilities, not authorization to execute all of them.

| Internal concept | Actual advertised MCP name | Adapter requirement |
| --- | --- | --- |
| `mail.send` | `send_email` | Convert `to` string to array, `body` to `body_text` or `body_markdown`; supply native idempotency key; normalize the provider response into a receipt |
| sent-mail reconciliation | `list_sent_mail`, `search_mail`, `get_email` | Scope sender/mailbox, honor pagination, match the exact artifact and payload |
| work-order document | `create_document`, `get_document`, `update_document` | Persist provider document ID; retries update it rather than create another document |
| `calendar.invite` | `create_event` | Treat attendee notifications as an external commit; validate the live operation schema |
| `tasks.create` | `create_task` | Persist returned task ID and dedupe task creation before considering replay safe |
| `crm.update` | `update_contact`, `update_deal` and more specific operations | Choose a real entity/operation and revision; a generic `{workOrder, step, detail}` payload is not an API contract |

The current names such as `mail.send` are internal aliases. Do not expose all discovered provider tools to the planner or put `send_email` in the reversible registry: the current `COMMIT_TOOLS` set only recognizes its internal aliases. Keep a reviewed mapping from internal capability to provider operation, including input schema, side-effect classification, approval policy, idempotency mechanism and receipt lookup. Provider hints help describe a tool; the MCP specification explicitly treats annotations as untrusted unless their source is trusted. [MCP tools specification](https://modelcontextprotocol.io/specification/2025-06-18/server/tools).

**The premise behind D9 needs revision.** Current official docs and the actual `send_email` MCP schema advertise both `Idempotency-Key` and `idempotency_key`, capped at 255 characters. The documented scope is sender plus mailbox: same key and payload return the original send; a changed payload returns 409; the header takes precedence over the body. This is stronger than searching for a marker in the message body. Retain the local ledger and reconcile uncertain responses, but prefer the provider's retry key in a future adapter. Do not claim production dedupe was verified: no send, retry, payload-conflict, TTL, concurrency or delivery-state experiment was performed. [Ambiguous reliability documentation](https://www.ambiguous.ai/llms.txt), [current OpenAPI contract](https://app.ambiguous.ai/api/openapi.json).

The advertised send schema also exposes scheduling and undo-send options. Validate what a returned ID means—accepted, scheduled, sent or delivered—before labeling a receipt. An external resource ID alone is not proof of recipient delivery.

Official Ambiguous plugins exist for Codex and Claude Code and currently teach their host to use the CLI. They do not ship an MCP server or add an adapter to this repository. A developer plugin is useful for manual inspection; it is not the worker's execution policy. [Official Ambiguous plugins](https://github.com/ambiguous-ai/plugins).

## Newly merged mirror: offline findings

`node scripts/review-mirror.mjs` performs no external calls. Its parent intercepts `fetch`; two child processes redirect every mocked provider request to a local loopback server. It uses fake credentials and temporary state only. Nine desired-behavior checks produced one pass and eight failures; the fixed single-camera-file case is a scope limitation, not an accidental corruption claim.

- **Only one process coalesces creation.** Two concurrent calls within a single process create one document. Two separate processes both see no stored mapping, both create a document, and retain only one ID in `mirror-docs.json`. The reproduced provider call count is two. Creation also has the already-documented provider-success/mapping-write crash window. Before worker and listener both write mirrors, choose a single durable projection owner or protect mapping creation with a cross-process protocol and provider dedupe/reconciliation.
- **Any `ToolError` is treated as evidence a document is missing.** In `src/mirror/ambiguous.ts`, an update tool error followed by a get tool error causes creation. The probe returned temporary-backend-failure tool errors for both operations while the existing document remained present; the client still called `create_document`. Only a verified missing/trashed result should authorize recreation. Permission errors, rate limits and transient failures should leave the current mapping intact and retry later.
- **Configured endpoint is ignored.** `AMBIGUOUS_MCP_URL` is unused; `ENDPOINT` is fixed to production. The mock observed the production URL even when the configuration pointed to a local test endpoint. Honor the configured origin before attaching its credentials.
- **JSON-RPC stream handling is incomplete.** The client accepts a response with a different request ID and rejects an SSE stream whose first JSON message is a progress notification followed by the valid response. Parse complete events and select the response matching the outgoing ID, rather than the first parseable line. These are mock protocol edge cases; the real provider was not made to emit them.
- **The document does not show what was drafted or approved.** `renderWorkOrder` displays statuses, constraints, approver and receipt but omits `Step.output`, `LedgerEntry.args`, full payload hash and work-order approver allowlist. A viewer cannot inspect the email text or recipient before an approval from this document. Add the canonical draft and frozen proposed arguments as evidence sections, labeled with their revision.
- **The local fallback is one shared camera file.** Mirroring A then B leaves only B in `state/workorder.md`. Keep that intentional focused-camera view if useful, and add per-work-order files or an index before showing two customers concurrently.

Do not run `src/mirror/mirror.check.ts` assuming `MIRROR_MODE=file` guarantees an offline test. Its invalid-key section deletes `MIRROR_MODE` and makes a production request with an invalid credential. With a configured key it also creates and deletes a real document. This review did not run that script. The source lane's reported live checks are its own evidence, separate from these mocked tests.

`mirrorSoon` is a sensible nonblocking call surface, but fire-and-forget alone does not durably schedule a projection. Once lifecycle calls are integrated, retain pending projection work in durable state so the final update can be retried after process death; expose mirror lag separately from job status. SQLite must continue to decide business state.

## Dataset pack and concrete demo extensions

`scenarios/review/banking77-sample.json` contains six unchanged utterances selected from the 3,080-row test split, one each for delivery, refunds, duplicate charges, profile changes, transfer cancellation and account closure. The original source commit, record index, SHA-256, attribution and CC BY 4.0 license are retained. `cases.json` adds synthetic internal-only policies and injection wrappers; these additions are not original benchmark annotations. [Original BANKING77 dataset](https://github.com/PolyAI-LDN/task-specific-datasets), [paper](https://aclanthology.org/2020.nlp4convai-1.5/).

The main checkout's untracked `datasets/README.md` and `notes/dataset-import.md` were read only. That pack has richer local Northwind/Acme/Lantern cases and skip-ahead states, but its import note correctly says there is no runtime loader and that IDs/approvers need normalization. Do not import arbitrary recovery JSON directly into a live ledger. Validate customer ownership, step IDs, ledger-key prefixes, receipt ownership and real approvers first; derived fixtures should remain isolated.

After grounding is fixed, three useful demo extensions are:

- **Show two customers interleaved.** Alternate an outage response with a refund question, pause both, kill the worker, then resume. The visible invariant is that recipients, restrictions and evidence stay with their own work orders. The public-data test already revealed why this is necessary.
- **Let the audience inject a proposed shortcut.** Show the hostile forwarded text beside the extracted restriction, proposed payload and absent send receipt. Make explicit whether the model rejected the request, the deterministic policy blocked it, or a human denied it. These are distinct protections worth showing.
- **Demonstrate a correction after approval.** Change the proposed recipient or draft, show the payload diff and invalidate approval for the old hash. This requires proposal revision support; do not advertise it as implemented. It gives a human a concrete answer to “what exactly did I approve?”

For a larger second corpus, Bitext publishes synthetic support requests covering orders, delivery, cancellation and refunds under CDLA-Sharing-1.0. It is a better domain fit for retail support than BANKING77, but was researched only, not downloaded or tested here. Preserve its different license and provenance when importing. [Bitext dataset card](https://huggingface.co/datasets/bitext/Bitext-customer-support-llm-chatbot-training-dataset), [publisher's explanation](https://www.bitext.com/blog/free-customer-support-dataset/).

## Repeatable verification flow

1. Run `node scripts/review-planner.mjs` from this worktree. It ignores external model credentials by default, blocks non-loopback requests, uses temporary core state, reports desired-behavior failures and deletes temporary state. Add `--strict` for a failing exit status while findings remain. This does not reset the main demo.
2. Inspect the JSON reports case by case. Match the actual plan origin, input scenario, executed step outputs, pending ledger args and outbox count. Duplicate checks for one root cause should not be mistaken for independent incidents.
3. When intentionally checking a live model, use the documented `--live --config /absolute/path/.env` form. The harness reads only model configuration fields into the process, caps total HTTP sends at four including retries and adds a 45-second request deadline. It exercises two scenarios and never approves a commit. Existing captured results need no paid rerun merely to inspect them.
4. Run `node scripts/review-mirror.mjs` for the isolated document/protocol probes. Before enabling lifecycle document writes or external commits, make their adapter contracts concrete: select identity, map names and payloads, parse provider error/receipt envelopes, verify key length and preserve the exact approved payload. First test those behaviors against deterministic mocked transport. Email is still a separate adapter from the newly merged document client.
5. In a designated test workspace with an explicitly chosen recipient, separately verify native same-key retry, changed-payload 409, provider-accepted/local-ledger-missing recovery, pagination and uncertain outcomes. No such write test occurred in this review. Ambiguous's disposable public sandbox supports synthetic task CRUD and expressly excludes mail and MCP, so it cannot prove email recovery. [Sandbox scope](https://www.ambiguous.ai/sandbox.md).

For the demo, show four linked facts on screen: the source request, the stored draft and constraints, the named approval for its payload hash, and the provider/outbox receipt. The current review observer can present actual local evidence; a future AG-UI projection should consume the same durable facts instead of treating transient model events as business completion.
